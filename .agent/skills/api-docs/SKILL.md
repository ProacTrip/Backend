# api-docs

## Trigger

When the user needs to generate or update API documentation for any ProacTrip module.

Keywords: `documentar API`, `generar docs`, `api docs`, `documentación endpoint`, `actualizar docs`, `documenta el módulo`, `docs del módulo`

---

## Critical Principle

**THIS SKILL READS ACTUAL CODE — NOT TEMPLATES.**

Documentation is generated by reading source files: `handler.go`, `command.go`, `response.go`, `domain/errors.go`, and `internal/bootstrap/app.go`. Every field, error code, header, and validation rule in the output MUST be verifiable in the source. If the code changes, re-running this skill must produce updated docs automatically.

**Never invent fields, error codes, or validations. If it's not in the code, it's not in the doc.**

---

## Pre-Flight Questions

Ask ONLY what the source code cannot answer. Read code first, then ask if something is still unclear.

| Question | Why code can't answer it |
|----------|--------------------------|
| ¿Qué módulo o feature querés documentar? (ej: `auth`, `user`, `search/flights`) | Entry point to find the right files |
| ¿Hay endpoints planificados (🚧) que quieras incluir como stubs? | Planned features have no code to read |
| ¿El endpoint tiene fases secuenciales? (ej: `outbound_selection` → `return_selection`) | Business flow not always obvious from handler names |

Do **not** ask about auth requirements, rate limiting, CORS, or cache — those are readable from `internal/bootstrap/app.go` and `handler.go`.

---

## Code-Reading Algorithm

### Step 0: Discover module structure

Before reading anything, map the module's file tree:

```
internal/modules/{module}/
├── domain/
│   ├── errors.go          ← sentinel errors (use Go variable name as error identifier)
│   └── {entity}.go        ← domain types used in responses
├── features/
│   └── {feature}/
│       ├── handler.go     ← HTTP method, path, headers, cookies
│       ├── command.go     ← request body schema + validation (+ response struct in some features)
│       └── response.go    ← response schema (may not exist; check command.go if missing)
internal/bootstrap/
└── app.go                 ← route groups, middleware chain, CORS
```

Also check `internal/shared/` for:
- `http/error_mapper.go` — `MapError()`, `MapHTTPErrorToProblem()`, `GetOrGenerateTraceID()`
- `http/cookies.go` — `SetAuthCookiesFromTokens()`, `ClearAuthCookies()`, cookie attributes
- `errors/errors.go` — `ProblemType` constants, `RegisterDomainErrorMapper` / `MapDomainError` registry, `HTTPStatusFromType()`

### Step 1: Read `internal/bootstrap/app.go` → Extract routes and middleware

For each route group find:
- Route prefix (`/v1/auth`, `/v1/search`)
- Middleware chain per group (auth required? rate limit tier? anon cookie?)
- CORS configuration (allowed origins, credentials, headers, max-age)
- Whether a route is public, authenticated, or uses API keys

```go
// Example: reading internal/bootstrap/app.go
authGroup := e.Group("/v1/auth")
authGroup.Use(middleware.RateLimitAnon())          // → Tier 3 anon rate limit
authGroup.POST("/register", registerHandler.Handle)
authGroup.POST("/login", loginHandler.Handle)

authProtected := authGroup.Group("")
authProtected.Use(middleware.RequireAuth())         // → requires access_token cookie
authProtected.POST("/logout", logoutHandler.Handle)
```

### Step 2: Read `handler.go` → Extract response headers and cookie ops

For each handler extract:
- HTTP method and full path (confirm against Step 1)
- `Cache-Control` headers set via `c.Response().Header().Set(...)`
- Cookie reads: `c.Cookie("__Secure-access_token")`
- Cookie writes: which cookies are set, cleared (`Max-Age=0`), or both
- `Clear-Site-Data` header usage on logout

```go
// Example: handler.go
func (h *Handler) Handle(c *echo.Context) error {
    c.Response().Header().Set("Cache-Control", "no-store, private")
    // → cache: no-store, private
    var cmd Command
    if err := c.Bind(&cmd); err != nil { return httperr.MapError(c, err) }
    resp, err := h.usecase.Execute(c.Request().Context(), cmd)
    // Read Set-Cookie calls in usecase or handler response writer
}
```

### Step 3: Read `command.go` → Extract request schema

Parse the Command struct and its `Validate()` method:
- JSON field names (from `json:"..."` tags)
- Types
- Required vs optional (from `Validate()` — missing required fields return errors)
- Validation rules (min length, max length, format, enum values)
- Default values (from struct initialization or handler pre-processing)
- Path params and query params if applicable (from `c.Param(...)`, `c.QueryParam(...)`)

```go
// Example: command.go
type Command struct {
    Email     string `json:"email"`     // Validate: required, valid email
    Password  string `json:"password"`  // Validate: required, min 8 chars
    FirstName string `json:"first_name"` // Validate: optional, max 100 chars
}
```

### Step 4: Read `response.go` → Extract response schema

- Read the Response struct. If `response.go` doesn't exist, check `command.go` for a `Response` or `UserResponse` type.
- Resolve type aliases to their domain definition (e.g. `type Response = domain.UserResponse`)
- Note `omitempty` / `omitzero` fields — document them as "omitido cuando..."
- Note nullable fields (`*string`, `*uuid.UUID`) — document as "puede ser null"
- For nested objects, document sub-field tables

```go
// Example: response.go (or command.go if no separate response file)
type Response = domain.UserResponse  // resolve alias → read domain/user.go

// domain/user.go
type UserResponse struct {
    ID            uuid.UUID  `json:"id"`
    Email         string     `json:"email"`
    EmailVerified bool       `json:"email_verified"`
    RoleName      string     `json:"role_name"`
    AvatarURL     *string    `json:"avatar_url,omitzero"` // omitted when nil
}
```

### Step 5: Read `domain/errors.go` + error mapper → Extract full error table

Three reads required:

**5a. `domain/errors.go`** — sentinel errors. Use the Go variable name as the error identifier:
```go
var (
    ErrInvalidIP        = errors.New("dirección IP inválida")
    ErrLocationProvider = errors.New("proveedor de ubicación no disponible")
)
```
→ `Código` for the doc table: always use the Go variable name (`ErrInvalidIP`, `ErrLocationProvider`)

**5b. Module error mapper** — find the mapping from error codes to ProblemTypes. Modules register their mappers via `RegisterDomainErrorMapper` (registry pattern), typically in `module.go` or a separate file. Read it to extract which ProblemType each error code maps to:
```go
// auth module example: error_mappings.go or module.go
func registerAuthErrorMappings() {
    serrors.RegisterDomainErrorMapper(func(err error) *serrors.Problem {
        switch {
        case errors.Is(err, domain.ErrEmailAlreadyExists):
            return serrors.ErrConflict(err.Error(), err)
        case errors.Is(err, domain.ErrInvalidEmail):
            return serrors.ErrInvalidEmail(err.Error(), err)
        }
        return nil
    })
}
```

**5c. Shared error definitions** (`internal/shared/errors/errors.go`) — maps each ProblemType to HTTP status:
```go
const (
    ProblemTypeConflict     ProblemType = "https://api.proactrip.com/errors/conflict"
    ProblemTypeInvalidEmail ProblemType = "https://api.proactrip.com/errors/invalid-email"
)
// HTTPStatusFromType() maps ProblemType → HTTP status code
```

This produces the full 4-column error table. Never omit the `Problem Type` column.

### Step 6: Generate documentation following the Output Conventions below

## Output Conventions (mandatory)

### Language

**All documentation is written in Spanish.** No exceptions.

This includes: section headers, table headers, table content, body text, inline notes, curl example comments, and `>` blockquotes.

The only things that remain in English/original form: HTTP method names (`GET`, `POST`), header names (`Content-Type`, `Cache-Control`), JSON field names, error codes (`EMAIL_ALREADY_EXISTS`), cookie names (`__Secure-access_token`), and code blocks.

### Status markers

Used in the Index table and section headers:

| Marker | Meaning |
|--------|---------|
| ✅ Implementado | Endpoint exists and is functional in the current codebase |
| 🚧 Planificado | Endpoint is designed but not yet implemented — stub only |

### Index format

Always a table (not a list):

```markdown
| Endpoint | Estado |
|----------|--------|
| [Arquitectura](#arquitectura) | ✅ |
| [Register](#register) | ✅ Implementado |
| [Login MFA](#login-mfa) | 🚧 Planificado |
```

### Error table schema

**Always 4 columns. No exceptions.**

```markdown
| Código | HTTP | Problem Type | Cuándo |
|--------|------|-------------|--------|
| `ErrEmailAlreadyExists` | 409 | `conflict` | Email ya registrado |
```

- `Código` — the Go variable name of the sentinel error (e.g. `ErrInvalidIP`, `ErrEmailAlreadyExists`), always in backticks
- `HTTP` — numeric status code only
- `Problem Type` — the slug used in the `type` URL field of the RFC 9457 response, in backticks. Extracted from ProblemType constants in `internal/shared/errors/errors.go`
- `Cuándo` — brief human description in Spanish of when the error occurs

### Planned features (🚧 stubs)

A planned endpoint gets a stub section — no full request/response docs since there is no code to read:

```markdown
## Login MFA 🚧

> 🚧 **Planificado — no implementado.** [Brief description of what this will do].
> El endpoint actual de login devuelve directamente las cookies de sesión sin requerir MFA.

---
```

### Diagrams

Include an ASCII flow diagram when the endpoint involves a multi-step interaction (OAuth, multi-phase search, SSE). Skip for simple request-response endpoints.

### Cookie examples

Always show the real `Set-Cookie` header format with all attributes:

```
Set-Cookie: __Secure-access_token=v4.local.eyJ...; HttpOnly; Secure; SameSite=Lax; Path=/; Domain=.proactrip.com; Max-Age=900
```

### Curl examples

One curl example per endpoint, using `{base_url}` as placeholder. Always include `Content-Type` if there's a body. Use `-c cookies.txt -b cookies.txt` for authenticated endpoints.

## Rules

| Regla | Categoría | Severidad | Check |
|-------|-----------|-----------|-------|
| D1 | Lectura de código | CRÍTICO | Leer `handler.go` para method, path, headers, cookies — nunca asumir |
| D2 | Lectura de código | CRÍTICO | Leer `command.go` para todos los campos, tipos y validaciones del request |
| D3 | Lectura de código | CRÍTICO | Leer `response.go` (o `command.go`) para campos de respuesta — resolver type aliases hasta el struct concreto |
| D4 | Lectura de código | CRÍTICO | Leer `domain/errors.go` + module error mapper + `internal/shared/errors/errors.go` para los 4 campos de la tabla de errores |
| D5 | Lectura de código | CRÍTICO | Leer `internal/bootstrap/app.go` para route prefix, middleware chain y CORS |
| D6 | Idioma | OBLIGATORIO | Todo el doc en español. Solo en inglés: nombres HTTP, headers, JSON keys, error codes, bloques de código |
| D7 | Tabla de errores | OBLIGATORIO | Siempre 4 columnas: Código — HTTP — Problem Type — Cuándo. Sin excepciones |
| D8 | Features planificadas | OBLIGATORIO | Endpoints 🚧 solo reciben un stub. No documentar request/response sin código que leer |
| D9 | Verificabilidad | OBLIGATORIO | Cada campo, código de error y header en el doc debe tener su origen identificable en el código |
| D10 | Formato de índice | DEBE | El índice es una tabla con columna Estado (✅ / 🚧). No usar listas |
| D11 | Response struct | DEBE | Si no existe `response.go`, buscar el struct `Response` en `command.go` |

## Verification Checklist

Run after generating any doc:

```bash
# Resolve module doc path
DOC="docs/{MODULE}_API.md"

# D1 — Every documented endpoint has a corresponding handler read
# Manually confirm: grep routes from internal/bootstrap/app.go, check each is in doc

# D4 — All domain error codes are documented
# Handles both patterns: "CODE: message" (auth) and plain "message" (environment)
grep 'Err[A-Z]' internal/modules/{module}/domain/errors.go | \
  grep -oP 'Err\w+' | \
  while read varname; do
    grep -q "$varname" "$DOC" && echo "✅ $varname" || echo "❌ MISSING: $varname"
  done

# D6 — No English section headers leaked into doc
grep -E '^## (Request|Response|Possible Errors|Security Notes|Overview)' "$DOC" \
  && echo "❌ English headers found" || echo "✅ Language OK"

# D7 — All error tables have 4 columns
grep -A1 'Posibles Errores' "$DOC" | grep '|' | \
  awk -F'|' '{if(NF-1 != 5) print "❌ Wrong column count: " $0}' \
  || echo "✅ Error tables OK"

# D3 — Response fields match response.go (or command.go) struct
# Manually confirm: compare JSON example fields with struct json tags
```

## Realtime Events (SSE) — Cross-Module Reference

### Central Endpoint

Todos los módulos publican eventos SSE a través de **un único endpoint**:

```
GET /v1/realtime/events
```

Conexión persistente mientras el usuario esté autenticado. El frontend mantiene una sola conexión y escucha eventos de todos los módulos.

### Convenciones de Documentación

Cuando documentes un módulo que emite eventos SSE:
1. Incluí una sección `## Realtime Events (SSE)` en el doc del módulo
2. Listá solo los eventos que ese módulo publica
3. Referenciá el endpoint central `/v1/realtime/events`
4. No documentes endpoints SSE por recurso (ej: NO `GET /v1/user/documents/:id/events`)

### Catálogo de Eventos

| Módulo | Evento | Descripción |
|--------|--------|-------------|
| **Auth** | `session.invalidated` | Sesión invalidada (admin bloqueó usuario, cambio de contraseña) |
| **User** | `user.avatar.updated` | Avatar procesado y activado por el worker |
| **User** | `user.profile.updated` | Perfil modificado |
| **Documents** | `document.processing.completed` | Documento procesado exitosamente por OCR |
| **Documents** | `document.processing.failed` | Error técnico durante procesamiento OCR |
| **Documents** | `document.verification.updated` | Admin cambió el estado de verificación |
| **Medical** | `medical.conflict.created` | OCR detectó un conflicto médico |
| **Medical** | `medical.conflict.resolved` | Usuario resolvió un conflicto médico |

### Formato de Evento

Todos los eventos SSE usan este formato:

```
event: {module}.{entity}.{action}
data: {"key": "value", ...}
```

El campo `event` usa notación de puntos: `{module}.{entity}.{action}`.

### Reglas para documentar eventos

1. **No duplicar**: Si un evento ya está en este catálogo, solo referencialo.
2. **Payload mínimo**: Documentar solo los campos necesarios para que el frontend actualice estado.
3. **No incluir datos completos**: SSE notifica cambios. El frontend obtiene el estado completo vía REST si necesita más datos.
4. **Late-join**: Si el frontend se conecta después de un evento, consulta el estado actual vía REST.

### SSE vs Polling vs WebSockets

| Aspecto | SSE | WebSockets | Polling |
|---------|-----|------------|---------|
| Dirección | Backend → Frontend | Bidireccional | Frontend → Backend |
| Reconnect | Nativo del browser | Manual | N/A |
| Complejidad | Baja | Alta | Baja |
| Uso en ProacTrip | ✅ Principal | ❌ No usado | ❌ No usado |

**Decisión arquitectónica**: SSE para todo realtime. WebSockets no se usan porque el frontend nunca inicia comunicación en tiempo real — solo reacciona a eventos del backend.
